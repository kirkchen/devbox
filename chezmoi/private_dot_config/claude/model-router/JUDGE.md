# Eval 標註任務：判定這件工作最低需要哪一級模型

你會收到一批 AI coding agent 的派工紀錄。對每一筆，判定**最低哪一級模型足以把這件事做好**。

## 你看不到什麼，以及為什麼

你看不到當初實際用了哪個模型。這是刻意的——看得到就會被錨定，標出來的只是在複述當初的決定，這份標註就失去用途。不要猜、不要從 evidence 反推。

## 分級定義

| tier | 名稱 | 適用情況 |
|---|---|---|
| 0 | cheapest | 機械性工作。指示裡已經寫明要找什麼、要改什麼、或要寫的程式碼本身。執行者照做加驗證即可，不需要做任何取捨 |
| 1 | mid | 需要先讀懂既有程式碼才能動手，或需要在已界定的框架內做判斷。大部分附了檢查清單的 review 屬於這級 |
| 2 | top | 必須自己拆解問題、在多個設計方案之間權衡、或診斷成因不明的錯誤。**或者**漏判的後果是缺陷會默默進到主線而沒有其他關卡會攔 |

## 最容易犯的錯

**不要用指示的長度判斷難度。** 一份把每個要檢查的項目都列出來的指示會很長，但那讓工作變**簡單**，不是變難。指示越完整、需要的模型越低。

反過來，一句「把這個 bug 修掉」很短，但可能是 tier 2。

## 判斷順序

1. 先問：**指示有沒有把「怎麼做」交代完？** 交代完了就往 0 或 1 靠。
2. 再問：**執行者需不需要自己做決定？** 需要取捨、需要選方案，往 2 靠。
3. 最後問：**做差了會怎樣？** 如果漏掉的東西不會有別人再攔一次（安全性、資料正確性），下限拉到 1 以上，就算前兩題都指向 0。

## 每筆你會拿到

- `task_prompt`：當初派工的完整指示
- `evidence.tool_calls_used`：執行者實際呼叫了幾次工具
- `evidence.wall_clock_s`：花了多久
- `evidence.needed_fix_round_afterwards`：事後有沒有被要求重做（`true` = 產出沒過 review）
- `actual_output`（可能沒有）：執行者實際交出的內容

evidence 怎麼用：
- `needed_fix_round_afterwards: true` 是明確的負面訊號——當初那個配置不夠。你標的 tier 應該**高於**能產出這種結果的水準。
- `tool_calls_used` 很高可能代表執行者在繞路，也可能代表工作本身就瑣碎。跟 `task_prompt` 對照再判斷，不要單看數字。
- `actual_output` 有的話最重要：直接看產出的深度。如果它只是把指示裡列的項目逐條回覆，那 tier 就低；如果它找出了指示沒點名的問題，那 tier 高。

## 輸出

只輸出一個 JSON 陣列，不要有其他文字：

```json
[
  {
    "id": "ev-050",
    "expected_tier": 1,
    "confidence": "high",
    "note": "指示列出 7 條 spec 契約與 6 個要檢查的風險點，範圍完全界定；但要讀 diff 與既有程式碼才能驗證，不只是照抄"
  }
]
```

- `expected_tier`：0、1 或 2
- `confidence`：`high` | `low`。判不準就寫 `low`，不要硬給。標錯比標成 low 傷害大。
- `note`：一句話，要引用 `task_prompt` 裡的具體內容當依據，不要寫「這個任務比較複雜」這種話。
